# 2. Data Model

Recreate the tables exactly. Column names stay `snake_case` because the JSON contract uses the same names. On the entities, set TypeORM's `name` option on each column, or configure a snake-case naming strategy once.

## 2.1 Shared base

Forms, entries and notifications all share: a ULID primary key, `created_at`, `updated_at`, and soft-delete `deleted_at`. Exports have a ULID and timestamps but no soft delete.

```ts
// src/common/db/ulid-entity.ts
export abstract class UlidEntity {
    @PrimaryColumn({ type: 'char', length: 26 })
    id!: string;

    @BeforeInsert()
    assignId() {
        this.id ??= ulid().toLowerCase();
    }

    @CreateDateColumn({ name: 'created_at' }) createdAt!: Date;
    @UpdateDateColumn({ name: 'updated_at' }) updatedAt!: Date;
}

export abstract class SoftDeletableUlidEntity extends UlidEntity {
    @DeleteDateColumn({ name: 'deleted_at' }) deletedAt!: Date | null;
}
```

TypeORM's `find*` methods exclude soft-deleted rows automatically. Laravel does the same, and route model binding returns 404 for a trashed record. Keep that behaviour, and pass `withDeleted: true` **only** where Laravel uses `withTrashed()`:

- Route lookups for `POST forms/:form/restore`, `POST entries/:entry/restore`, `DELETE entries/:entry/force` and `POST notifications/:notification/restore`.
- The entry list and export when `filter[trashed]` is `with` or `only`.
- Bulk `restore` / `force_delete`.
- The Postmark webhook's recipient lookup.
- Account deletion.

Note the reverse case too: loading an entry's or notification's **form** relation must exclude a soft-deleted form, because the ownership check relies on it being missing (ch. 3 §3.3).

Model IDs are **lowercase** ULIDs (`HasUlids` lowercases them). Schema field IDs in `forms.schema` are generated by clients or by `Str::ulid()` and are usually **uppercase**. Don't normalise those: they're data and are compared exactly. Match route IDs case-insensitively, because clients may have stored either form.

## 2.3 Relations and JSON shapes

```ts
@Entity('forms')
export class Form extends SoftDeletableUlidEntity {
    @ManyToOne(() => User, { nullable: false })
    @JoinColumn({ name: 'user_id' })
    user!: User;
    @Column({ name: 'user_id' }) userId!: number;
    @Column({ length: 400 }) name!: string;
    @Column({ default: false }) active!: boolean;
    @Column({ type: 'simple-json', nullable: true }) schema!: FormField[] | null;
    @Column({ type: 'simple-json', nullable: true }) settings!: Partial<FormSettings> | null;
    @OneToMany(() => FormEntry, (e) => e.form) entries!: FormEntry[];
    @OneToMany(() => FormNotification, (n) => n.form) notifications!: FormNotification[];
    @OneToMany(() => FormEntryExport, (x) => x.form) entryExports!: FormEntryExport[];

    /** Fields sorted by `order`; ties keep their stored order (stable sort). */
    orderedSchema(): FormField[] {
        return [...(this.schema ?? [])].sort((a, b) => a.order - b.order);
    }
}

export interface FormField {
    id: string; // ULID, unique within the schema
    order: number; // integer
    label?: string | null;
    name?: string | null; // input name; defaults to id
    rules?: string[] | string; // Laravel rule strings
}

export interface FormSettings {
    redirect: string | null; // default null
    timezone: string | null; // default null
    domains: string[] | null; // default []
    message: string | null; // default null
    honeypot_enabled: boolean; // default false
    honeypot_name: string | null; // default null
}
```

- Use `simple-json` on SQLite and `jsonb` on Postgres.
- `schema` keeps the order the client sent. Only presentation (API, emails, CSV) sorts by `order`. `Array.prototype.sort` is stable in Node 22, which matches Laravel's `sortBy`.
- Stored `settings` may be missing keys, for example rows written before a setting existed. Always read them through a `withSettingsDefaults()` helper that fills in every key, so the API returns all six (ch. 3 §3.4).
- Expose the FK columns (`userId`, `formId`) as plain properties so presenters don't need to load relations.

## 2.4 Migrations

- Write the initial migration by hand, or generate it and then review it. Don't rely on `synchronize` anywhere except the in-memory test database.
- Use one migration per table, in this order: users → password_reset_tokens → denied_tokens → forms → form_entries → form_notifications → form_entry_exports.

## 2.6 Data migration from Laravel

Write a one-off script (`scripts/import-from-laravel.ts`) that reads the Laravel database and inserts rows into the new schema:

1. Copy `users` rows as-is, including `token_version`. bcrypt hashes stay valid (ch. 5 §5.8).
2. Copy `forms`, `form_entries` and `form_notifications` as-is, including soft-deleted rows. `user_agent_display` is a JSON string. Copy it verbatim.
3. Assert every non-null `forms.schema` is a JSON **list** whose items have `id` and `order`. The Laravel app no longer reads the old object-keyed shape. Stop the import and report any form that fails this check.
4. Don't copy `denied_tokens`, `password_reset_tokens`, `form_entry_exports` or export files. Rotate `JWT_SECRET` at cut-over, so old tokens die anyway (ch. 5 §5.10). Pending reset links and exports expire within hours. Ask users to re-request them.
5. Drain the Laravel queue before the final import, so no spam checks or alerts are lost or sent twice.

Rehearse the import against a copy of production data. Then run the contract suite against the imported database.
